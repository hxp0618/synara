## Goal

Remove the per-Turn foreground network `git fetch` from the warm claim critical path when the shared
Git cache is provably fresh, WITHOUT weakening the credential-revocation gate. Today
`docs/contracts/workspace-v1.md` mandates a credential-authorized network Fetch on every Turn "so a
warm cache cannot bypass a revoked Credential". The revocation authority that actually matters is the
per-Claim Workspace Credential Grant resolve (server-side, rechecks Binding/Credential
revocation/expiry under locks). Cache-first keeps that resolve mandatory and skips only the network
Git round-trip inside a bounded freshness window.

## Frozen design decisions

- D1 (revocation gate unchanged): every materialization still performs the Grant resolve for
  `git_fetch` exactly as today, BEFORE any cache reuse. Resolve failure fails the workspace exactly
  as today. No cache path may run without a successful resolve in the same claim.
- D2 (freshness window): new agentd knob `SYNARA_AGENTD_WORKSPACE_FETCH_FRESHNESS_WINDOW`
  (duration, default `0`). `0` = exactly today's behavior (always foreground fetch). When > 0: if the
  shared cache records a successful credentialed fetch for this exact repository fingerprint newer
  than the window, AND the cache can resolve the requested ref/base commit, the foreground fetch is
  skipped. Any doubt (missing marker, unparsable, missing ref, corrupt cache) falls back to the
  normal foreground fetch. Bound the accepted window to at most 1h at parse time.
- D3 (freshness marker): after every successful credentialed foreground or background fetch, write a
  marker file inside that repository's cache directory (owned under the existing cross-process cache
  lock; write-temp-then-rename; contains RFC3339 fetch time). Reading requires the cache lock the
  materialization already holds. The marker never stores credentials or URLs beyond what the cache
  directory layout already encodes.
- D4 (background refresh): when the foreground fetch was skipped, schedule ONE background refresh for
  that repository after the Provider is started: take the cache lock, run the same credentialed
  fetch, update the marker. Failures are logged (bounded) and do not affect the running Turn; the
  next claim's window check naturally degrades to a foreground fetch once the marker ages out.
  The background refresh must resolve its own credential via the same Grant (reuse the resolved
  credential from this claim's materialization — do not re-resolve after the Provider has started if
  that would extend credential lifetime beyond current semantics; simplest correct shape: run the
  background refresh with the already-resolved short-lived credential immediately after
  `workspace.ready`, concurrently with Provider start, not later).
- D5 (visibility): log one bounded structured line per materialization with outcome
  `fetched | cache-fresh-skip | fallback-after-skip-doubt`. Do NOT change the Worker Protocol or the
  workspace.ready payload in this increment (no new wire fields).
- D6 (contract): update `docs/contracts/workspace-v1.md` Repository network policy + preparation
  sections: the every-Turn foreground fetch statement becomes conditional on the freshness window
  (default preserves today's behavior verbatim), and the revocation sentence becomes "a warm cache
  cannot bypass Grant resolution: the per-Claim `git_fetch` Grant resolve remains mandatory and
  fail-closed; the freshness window bounds only the network staleness of objects already authorized".
  Document the marker, the fallback-on-doubt rule, and the bounded window.
