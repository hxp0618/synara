# Data Residency Boundary v1

Status: execution boundary implemented; full deployment annex required for a customer promise

`Tenant.region` is the Tenant home Region label. It is not, by itself, an enforcement control. The authoritative execution
boundary is the versioned Tenant Execution Scheduling Policy `region` allow-list. Routing filters every candidate through
the effective Tenant/Organization policy and locks the same policy head at placement commit; a concurrent policy change
causes the commit to fail rather than placing with stale authority. Cross-Region failover and evacuation cannot select a
destination outside the effective allow-list.

Tenant `owner|admin|security_admin` may narrow the execution Region list; auditors and controlled Support Access may read it.
The Settings surface downloads the exact server-generated bytes from `GET /v1/tenants/{tenantID}/data-residency-statement` as
`synara-data-residency-statement-v1`, containing the Tenant, home Region, policy version, digest, enforcement state and
allowed Regions. The client rejects a missing or stale byte header before download; the response is byte-bound with
`X-Synara-Data-Residency-SHA256`, `X-Synara-Data-Residency-Bytes`, and `Content-Length`, and the export is recorded as
`tenant.data_residency_statement_exported` in the Tenant audit log. An
unrestricted statement is evidence of no execution promise, not evidence of global residency. Once an allow-list is active, the legacy Tenant update path locks the same policy authority and rejects
a home Region outside the list; widening the policy, changing the home Region and narrowing it again remain explicit,
versioned operations rather than an implicit bypass.

A full customer residency promise additionally requires a signed deployment annex that identifies:

- PostgreSQL primary, replica, backup and restore-processing Regions;
- object storage primary, replica, backup and deletion-processing Regions;
- KMS/HSM key and key-backup Regions;
- Queue, logs, traces, metrics, incident bundles and Support processing Regions;
- subprocessors and Provider request-processing/retention Regions;
- disaster-recovery destinations, customer opt-in semantics and the behavior when no allowed destination is ready;
- effective date, Tenant, environment, artifact/image digests, approvers and review expiry.

The annex must match the runtime inventory and a failover/evacuation acceptance report. If any plane is unknown, global, or
outside the promised list, its status must be `deployment-annex-required` or explicitly disclosed; sales/UI must not shorten
an execution-only boundary into “all data stays in Region.”

`scripts/stage6-residency/validate_data_residency_evidence.py` turns the Annex, runtime inventory, downloaded browser
statement, failover/evacuation exercises and separate Operations/Security/Privacy-Legal approvals into
`synara.data-residency-deployment-evidence-receipt.v1`. The deployment manifest is only an index of eight unique path/hash
references. Every referenced file is strict UTF-8 JSON with the same Tenant, candidate/commit/lockfile/environment,
Artifact/Migration and policy-head subject. The validator derives its receipt from those files rather than accepting a
second set of manifest assertions.

`scripts/stage6-residency/prepare_data_residency_evidence.py` removes hand-authored manifest hashes without rewriting signed
attachments. Its path-only draft names the eight finalized files beneath one evidence root. The preparer stable-reads and
secret-scans bounded regular files, rejects duplicate JSON fields and unsafe paths, derives the manifest, validates the
complete semantic graph, and atomically publishes immutable `0600` manifest/receipt pairs with rollback on partial
publication. A failed declared exercise remains a valid ineligible receipt rather than being replaced by a passing attempt.

The Annex and runtime processing-plane inventories must match exactly. The browser statement must reproduce the common
policy subject. Both exercises bind the exact Annex/runtime digests, and each role approval binds the exact Annex, runtime,
browser and exercise digest set. Cross-Tenant/candidate/policy evidence, arbitrary hash-valid content, stale evidence,
duplicate roles/identities and invalid time order fail closed. The receipt publishes a deterministic `evidenceSetSha256`
over all eight attachment digests.

This v1 machine boundary validates schemas, content, subjects, hashes and temporal consistency; it does not perform
cryptographic signature, human identity, deployed-browser-origin, deployment-inventory-authority or live-exercise-authority
verification. Every attachment and receipt records that external verification is still required and that cryptographic
signatures were not verified. A file that claims otherwise is invalid. Only a full production/production-like evidence set
with all planes known, disclosed and within the sorted allowed Region set can become eligible for human review. The permanent
assessment is `evidence-validated-not-residency-approved`; real signed evidence and role approvals remain mandatory.
